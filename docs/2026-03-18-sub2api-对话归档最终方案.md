# sub2api 对话归档最终方案

> 已废弃（2026-03-19）。
> 当前仓库不再使用外置 Python `archive_proxy` 方案，本文件仅保留历史讨论。
> 请以 `docs/2026-03-19-sub2api-会话归档部署说明.md` 和 `docs/superpowers/specs/2026-03-19-sub2api-session-turn-archive-patch-design.md` 为准。

## 目标

在 **不修改 `sub2api` 源码**、**尽量少改现有部署结构** 的前提下，实现以下能力：

- 保存本地 `Codex` 与 `Claude Code` 发到服务器的请求内容
- 保存服务器返回给这两个客户端的响应内容
- 按“项目名称 / token 名称”归档
- 长期自动运行

当前服务器上已有两条链路：

1. `v2ray`
   - 外部入口：`443`
   - 路径：`/v2ray`
   - `Nginx` 解 TLS 后转发到 `127.0.0.1:10000`
2. `sub2api`
   - 宿主机端口：`127.0.0.1:8080`
   - 当前 `Nginx` 的 `location /` 直接反代到 `127.0.0.1:8080`

---

## 最终结论

推荐采用唯一方案：

```text
客户端
  -> HTTPS -> Nginx
  -> HTTP  -> Python 归档代理
  -> HTTP  -> sub2api
```

并且保持：

- `location /v2ray` 继续走 `127.0.0.1:10000`
- `location /` 改为走 `Python` 归档代理
- `Python` 再转发到 `127.0.0.1:8080`

这个方案满足以下要求：

- 不改 `sub2api` 源码
- 不改变 TLS 终止方式
- 不影响 `v2ray`
- 可以拿到明文请求与明文响应
- 可以作为常驻服务长期运行

---

## 为什么不需要抓 HTTPS 包

因为 `Nginx` 本身已经是 TLS 终止点。

也就是说：

- 客户端到 `Nginx` 是 HTTPS
- `Nginx` 到 `Python` 可以是本机明文 HTTP
- `Python` 到 `sub2api` 也可以是本机明文 HTTP

所以归档代理不需要：

- 被动抓包
- TLS 离线解密
- 读取会话密钥

你真正需要做的只是：

- 让 `Nginx` 把 `location /` 的请求先交给 `Python`
- 让 `Python` 在转发前后把内容落盘

---

## 归档范围

你当前并不需要保存整个站点所有流量，只需要保存：

- 本地 `Codex`
- 本地 `Claude Code`
- 与服务器之间真正上传和下发的对话内容

因此归档范围应当收窄为“真实对话接口”，不要保存前端页面、管理后台和探测类请求。

### 建议归档的接口

- `POST /v1/messages`
  - `Claude Code` 主对话入口
- `POST /v1/responses`
  - `Codex` OpenAI Responses 对话入口
- `POST /responses`
  - `Codex` 无前缀别名入口
- `POST /chat/completions`
  - `Codex` 或兼容客户端可能使用

### 建议跳过的接口

- `POST /api/event_logging/batch`
  - Claude Code 遥测，不是对话
- `POST /v1/messages/count_tokens`
  - 探测/估算请求，不是正式对话
- `GET /health`
- `GET /models`
- `GET /usage`
- 前端页面请求
- 静态资源请求
- 管理后台请求
- `/v2ray`

## Codex 链路分析

从本地 `codex` 源码和 `sub2api` 路由看，`Codex` 的主链路是：

- `POST /responses`
- `POST /v1/responses`
- `Accept: text/event-stream`

也就是 **HTTP + SSE**。

### 结论

- 常规文本对话，优先按 HTTP/SSE 处理即可
- 第一阶段只支持 HTTP/SSE，已经能覆盖绝大多数正常 `Codex` 对话

### 关于 WebSocket

`Codex` 代码里确实存在 Responses WebSocket 实现，但它不是默认必走路径。

因此建议：

1. 第一阶段
   - 重点做好 HTTP/SSE 归档
   - 遇到 `GET /responses` WebSocket Upgrade 时，至少保持透传不破坏
2. 第二阶段
   - 如果线上确认确实出现 `GET /responses` WebSocket 对话，再补做 WS 帧级归档

换句话说：

- 现在**不能断言 Codex 永远不用 WebSocket**
- 但可以确定：**HTTP/SSE 是必须支持的主路径**

### Codex 识别规则

当前实现中，`Codex` 路径不会只按 URL 归档。

还需要满足以下条件之一：

- `User-Agent` 显示为 `codex_cli_rs/`、`codex_vscode/` 等 Codex 客户端
- `originator` 以 `codex_` 或 `codex ` 开头

这样可以避免把其他 OpenAI 兼容客户端也一起归档。

## Claude Code 链路分析

从 `sub2api` 源码看，`Claude Code` 的主对话入口是：

- `POST /v1/messages`

`sub2api` 对 `Claude Code` 的识别逻辑主要依赖：

- `User-Agent` 匹配 `claude-cli/x.y.z`
- `system prompt`
- `X-App`
- `anthropic-beta`
- `anthropic-version`
- `metadata.user_id`

但对归档代理来说，不需要完全复刻它的严格校验逻辑。  
只要用于“是否要归档”的判定，建议使用更稳妥的轻量条件：

- 路径是 `POST /v1/messages`
- 且 `User-Agent` 以 `claude-cli/` 开头

这样就足够把 `Claude Code` 真正的对话流量筛出来。

## 项目名称与 token 名称

### token 名称

`token 名称` 在代理层并不能直接从明文请求里稳定拿到，因为真正的 API Key 名称在 `sub2api` 内部。

当前实现先采用简化方案：

- 从 `Authorization` / `X-API-Key` / `X-Goog-Api-Key` 中提取 key
- 如果配置了 token 映射文件，则优先映射为可读名称
- 否则仅保留前 7 个字符作为脱敏前缀
- 例如 `sk-test-secret-value` 归档为 `sk-test`

当前默认还会要求：

- 只有命中 token 映射文件的请求才会真正归档

这样可以进一步避免误归档非本地工具流量。

如果后续需要严格映射成后台里的人类可读 API Key 名称，再补数据库查询或外部映射表。

### 项目名称

当前 `Codex` 和 `Claude Code` 并没有一个通用且稳定的“项目名称”公共字段。

建议优先级如下：

1. 最推荐
   - 你自己在本地客户端注入自定义头，例如 `x-project-name`
2. 其次
   - `Codex` 侧从 `session_id` / `conversation_id` / `prompt_cache_key` 推导
3. 最后
   - 统一落到 `unknown_project`

当前实现先采用：

- 优先取 `X-Project-Name`
- 未提供时使用 `unknown_project`

## 最终部署结构

建议使用以下本机端口：

- `Nginx`: `443`
- `v2ray`: `127.0.0.1:10000`
- `Python` 归档代理: `127.0.0.1:18080`
- `sub2api`: `127.0.0.1:8080`

链路如下：

```text
/v2ray  -> 127.0.0.1:10000
/       -> 127.0.0.1:18080 -> 127.0.0.1:8080
```

---

## Nginx 需要做的修改

只改 `location /` 的上游，不动 `location /v2ray`。

### 修改目标

当前：

```text
location / -> 127.0.0.1:8080
```

修改后：

```text
location / -> 127.0.0.1:18080
```

而 `Python` 代理内部再去请求：

```text
127.0.0.1:8080
```

### 配置原则

1. `location /v2ray` 优先保留
2. `location /` 改为转发给 `Python`
3. 保持 Upgrade / Connection / X-Forwarded-* 这些代理头透传
4. 保持流式响应不缓冲

### 建议配置思路

以你当前站点结构，Nginx 逻辑应调整为类似：

```nginx
location /v2ray {
    proxy_pass http://127.0.0.1:10000;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection $connection_upgrade;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

location / {
    proxy_pass http://127.0.0.1:18080;
    proxy_http_version 1.1;
    proxy_buffering off;
    proxy_request_buffering off;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection $connection_upgrade;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

注意：

- `proxy_buffering off` 对 SSE 很重要
- `proxy_request_buffering off` 可以减少大请求体被 Nginx 先落盘再转发的问题
- 如果你现有站点已经有 `map $http_upgrade $connection_upgrade`，保持沿用即可

## Python 归档代理需要做的事

`Python` 服务不是旁路监控，而是正式代理。

它需要完成四件事：

1. 接收来自 `Nginx` 的明文 HTTP 请求
2. 判断这个请求是否属于需要归档的对话接口
3. 若需要归档，则保存请求体与响应体
4. 再把请求转发给 `sub2api`

### 归档判断逻辑

建议按如下顺序判定：

1. 如果路径是 `/v2ray`
   - 不应进入该服务
   - 若误进，直接拒绝或透传但不归档
2. 如果路径是以下之一，归档：
   - `POST /v1/messages`
   - `POST /v1/responses`
   - `POST /responses`
   - `POST /chat/completions`
3. 如果路径是以下之一，跳过：
   - `POST /api/event_logging/batch`
   - `POST /v1/messages/count_tokens`
   - `GET /health`
   - 其他页面、静态资源、后台接口

### 响应处理要求

1. 非流式响应
   - 完整读取后保存
   - 再返回给客户端
2. SSE 流式响应
   - 按 chunk 增量转发
   - 同时按原始字节流保存
3. WebSocket Upgrade
   - 第一阶段只做透传，不做归档
   - 至少不能破坏连接

## 目录结构建议

建议目录结构如下：

```text
archive/
  2026-03-18/
    <project_name>/
      <token_name>/
        <timestamp>_<request_id>/
          meta.json
          request.bin.gz
          response.bin.gz
```

### 字段建议

`meta.json` 中建议保存：

- 时间
- 方法
- 路径
- 查询参数
- `user-agent`
- `content-type`
- `x-request-id`
- `x-forwarded-for`
- `token_name`
- `project_name`
- 是否流式
- 是否命中归档规则
- 请求体原始大小
- 响应体原始大小
- 请求体是否被截断
- 响应体是否被截断

`request.bin.gz`

- 保存原始请求体

`response.bin.gz`

- 非流式时保存完整响应体
- SSE 时保存原始流式字节
- 若超过配置上限，只保存前 N 字节

## 长期运行方式

推荐把 `Python` 归档代理作为独立 `systemd` 服务长期运行。

原因：

- 它和 `sub2api` 解耦
- 重启方便
- 可单独看日志
- 后续升级 `sub2api` 不受影响

建议服务职责：

- 监听 `127.0.0.1:18080`
- 自动创建归档目录
- 支持按天切分
- 支持 gzip 压缩
- 支持保留天数清理
- 支持 token 映射文件
- 支持单文件大小限制

## 风险与控制

### 1. 敏感信息

归档内容会包含：

- prompt
- 工具参数
- 文件路径
- 代码片段

因此必须避免把以下内容写入文件名或目录名：

- 原始 prompt
- 原始路径
- 原始 token

### 2. 磁盘占用

SSE 长对话会持续增长。

建议至少加：

- 自动压缩
- 保留天数
- 单日目录切分
- 单请求大小上限

### 3. 兼容性

第一阶段先以 HTTP/SSE 为主，不做 WebSocket 内容归档。

这样可以：

- 先覆盖主要对话流量
- 避免把工程复杂度拉高

---

## 最终建议

最终建议只保留这一条路线：

1. 保持 `Nginx` 与 `v2ray` 现状不变
2. 只修改 `location /` 的上游到 `Python`
3. `Python` 再转发给 `sub2api`
4. 只归档以下真实对话接口：
   - `POST /v1/messages`
   - `POST /v1/responses`
   - `POST /responses`
   - `POST /chat/completions`
5. 明确跳过：
   - `/api/event_logging/batch`
   - `/v1/messages/count_tokens`
   - 页面、静态资源、后台接口
6. 第一阶段只处理 HTTP/SSE
7. WebSocket 先保证透传，二期再补归档

这套方案是当前约束下最干净、维护成本最低、且最接近你真实目标的实现方式。
